\subsubsection{Separation of the Three Data Components}

Each of the live store, exported files or daily aggregation job bears different responsibilities. 
Therefore, they are split into three separate parts each implemented by a different service. 

Live store is powered by Cloud SQL. 
Users can retrieve individual records via an ID, allowing the system to locate a specific row directly without needing to scan the entire data table. 
Data entry is also done on a per-record basis. 
Each commit operation adds a new row of data to the table.
Exported files are saved by Cloud Storage. 
This task involves exporting data from a database to a separate file. 
Once created, the content of this file remains static. 
Such products do not have a query function. 
It is only necessary to ensure that their content is complete and readable and can be stored for a long time.
Daily aggregation job is processed by Cloud Run Job. 
It scans all responses for the day, summarizes the results by category, and does not involve access to individual records. 
Repeating the process on the same day yielded the same result.

The live store does the work Bigtable did, reaching a record by its key rather than by scanning. 
Exported files are of the same kind as the files GFS held, complete and never edited after they are written. 
Counting a day of responses is what MapReduce was built to perform, and Cloud Run Job now carries it out. 
None of these systems was inherited. Their positions were taken over and the implementations replaced.

\subsubsection{Selected Service Model and Deployment Model}

The selected service model is PaaS, provided by Google Cloud Run. Under this model, application is packaged as a container deployed by the customer, and Google manages the underlying infrastructure, the operating system, and the runtime. A realistic IaaS alternative is Amazon EC2, which requires the customer to manage the virtual machine, operating system, scaling policy, etc. Amazon EC2 would be suitable if customized operating systems, persistent background processes, or host-level access were required.

In addition, the selected deployment model is public cloud, because the service runs on infrastructure operated by Google Cloud. A realistic alternative is hybrid cloud using an on-premises Kubernetes environment connected to public-cloud services. Public cloud is selected because it moves infrastructure management to the provider and supports rapid, elastic deployment. Hybrid cloud would be more suitable if sensitive information, regulatory requirements, or legacy systems had to remain on organization-controlled infrastructure.

\subsubsection{Rapid Elasticity and Resilience}

During a campaign peak, Google Cloud Run automatically creates additional container instances according to incoming requests, CPU utilization, and request concurrency. After the campaign traffic decreases, Google Cloud Run removes idle instances, and can scale to zero when no requests remain, to release unnecessary computing capacity.

If an application instance fails, Google Cloud Run stops routing requests to that instance. Other healthy instances continue processing requests, while replacement capacity is created. Since application data is stored externally in Google Cloud SQL rather than inside individual containers, replacing an instance does not cause persistent data loss.
